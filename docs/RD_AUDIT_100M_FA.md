# بررسی بازطراحی فاصله‌سنجی ۱۰۰ متر — ۲۰۲۶-۱۱-۰۴

وضعیت: بررسی اولیه کد و اجرای مجدد تست‌ها؛ **نسخه نهایی یا پذیرش میدانی نیست**.
مخزن مبنا person-car-detector است؛ مخزن person-car-detecto خالی بود.
گزارش‌های پیشین مخزن شواهد تاریخی‌اند و به‌عنوان آزمایش این نوبت بازنشر نشده‌اند.

## موجودی و نتیجه بررسی

۲۸ فایل Python در ریشه، ۹ فایل تست، قالب HTML، اسکریپت‌های نصب و گزارش‌های JSON بررسی شدند.
در checkout هیچ وزن ONNX/PT، ویدئو، تصویر کالیبراسیون یا دیتاست برچسب‌دار وجود نداشت.
models فقط منشأ، هش و مجوز دارد. README از مدل‌های bundled نام می‌برد اما فایل‌ها
در Git نادیده گرفته شده‌اند و در زمان بررسی GitHub Release هم وجود نداشت.
نصب‌کننده‌ها verify_models را اجرا می‌کنند و بنابراین clone تازه آماده اجرا نیست.

آزمایش تازه: `python -m pytest -q -ra`، ۸۱ passed در ۴٫۷۵ ثانیه، یک هشدار pytest plugin.
محیط Linux x86_64، CPU؛ دوربین گوشی و GPU در اختیار این اجرا نیست.
این تست‌ها شامل داده مصنوعی و mock هستند؛ عدد فوق نه FPS است نه دقت مدل.

## خطاهای هندسی تعیین‌کننده

خروجی فعلی Z عمق محور اپتیکی است، نه فاصله اقلیدسی دوربین تا هدف.
برای پیکسل مرجع (u,v)، پس از رفع اعوجاج:
R = Z sqrt(1 + ((u-cx)/fx)^2 + ((v-cy)/fy)^2).
باید مشخص شود مرجع اندازه‌گیری سطح جلویی، مرکز سه‌بعدی یا نقطه تماس با زمین است.
اندازه‌گیری لیزری سطح خودرو را نباید با عمق مرکز box سه‌بعدی بی‌قید مقایسه کرد.
از یک RGB با اندازه و حرکت نامعلوم، مقیاس مطلق شناسایی‌پذیر نیست.
VO/SfM تک‌چشمی بدون scale anchor این مشکل را حل نمی‌کند؛ اشیای متحرک نیز فرض صحنه ثابت را نقض می‌کنند.
Kalman نمی‌تواند bias فاصله کانونی یا اندازه فرضی غلط را حذف کند.

## معماری پیشنهادی، مشروط به آزمایش

تشخیص با وضوح اصلی و slicing انتخابی → tracker با زمان منبع → نمونه‌برداری عمق
از سطح هدف (ترجیحاً mask، نه میانه کل box شامل پس‌زمینه) → تبدیل Z به R با K →
کنترل کیفیت و دامنه → فیلتر مستقل [R, dR/dt] برای هر ID → API و JSONL.
مدل حرکت و شتاب برای Q، پراکندگی تصادفی برای R_measurement و کف خطای سیستماتیک
جدا نگهداری شوند. جمع‌کردن اطلاعات هم‌بسته مدل و هندسه با فرض استقلال ممنوع است.
برای تخمین ردشده raw تشخیصی ممکن است ثبت شود ولی distance_m معتبر باید null باشد.
پس از فقدان هدف، خروجی prediction باید صریحاً از measurement جدا باشد.

Metric3Dv2 و UniDepth کاندید teacher دقیق‌اند؛ هنوز برنده تجربی این پروژه نیستند.
نسخه گوشی: detector سبک + کنترل هندسی و در صورت تأیید آزمایش، depth student متریک.
ONNX Runtime CPU baseline است. NCNN/Vulkan و LiteRT/MNN باید روی خود گوشی مقایسه شوند؛
OpenVINO انتخاب عمومی برای Adreno نیست. INT8 فقط با calibration set مستقل از test
و ارزیابی افت تشخیص اهداف کوچک و فاصله پذیرفتنی است.

## معیار پذیرش جدید

برای هر کلاس جداگانه: P و R حداقل ۰٫۹، و Accuracy within 10% هدف ۰٫۸۵ تا ۰٫۹۰.
گزارش در ایستگاه‌های ۵،۱۰،۲۰،۳۰،۴۰،۵۰،۶۰،۷۰،۸۰،۹۰،۱۰۰ متر؛ signed relative error،
AbsRel، median relative error، MAE، RMSE و within 5/10/15%.
حتماً valid/eligible coverage و good/eligible را کنار good/valid گزارش کنید.
برای اعتماد آماری باید تعداد نمونه و تنوع scene ثبت و bootstrap در سطح sequence انجام شود؛
صد فریم متوالی یک هدف صد آزمایش مستقل نیست.

## داده‌های لازم برای تکمیل

ویدئوی اصلی گوشی (بدون rescale پیام‌رسان)، مدل دقیق دستگاه/SoC و RAM، camera ID،
رزولوشن و crop/zoom/focus، حداقل ۱۰ تصویر متنوع checkerboard با اندازه خانه معلوم،
و فاصله مرجع مستقل هر هدف با timestamp و تعریف نقطه اندازه‌گیری لازم است.
نام Redmi Note 9 معمولاً با Helio G85 همراه است؛ Snapdragon 720G/Adreno 618 معمولاً
به Note 9S/Pro مربوط است. شناسه سخت‌افزار باید از خود دستگاه خوانده شود.
تقسیم train/validation/test در سطح ویدئو، محل و زمان انجام شود.
COCO/Objects365 برای تشخیص اولیه؛ KITTI/KITTI-360/DDAD برای هندسه زمینی؛
nuScenes/Waymo/Argoverse با رعایت مجوز برای تنوع حسگر؛ BDD100K/Cityscapes برای
دامنه خیابان؛ DIODE برای depth و DENSE برای شرایط نامساعد. هیچ‌کدام جای
آزمایش فاصله و لنز گوشی مقصد را نمی‌گیرند. VisDrone فقط diagnostic اهداف کوچک هوایی است.

بدون این ورودی‌ها، fine-tuning مختص دوربین، تعیین برنده مدل، آزمون ۱۰۰ متر و
اعلام نسخه نهایی علمی ممکن نیست. ابزار ارزیابی افزوده‌شده آماده ورود داده واقعی است؛
هیچ فاصله مرجع از حدس ویدئو تولید نشده است.
